# Проверенные контракты iiko

Проверено 13.11.2026 по официальной [OpenAPI 3.0.4](https://api-ru.iiko.services/api-docs/docs). Снимок находится в `docs/iiko-openapi.json`; он нужен для аудита, приложение не отправляет его никуда.

Используются только POST-методы, читающие данные:

| Метод | Наличие в OpenAPI | Назначение |
|---|---|---|
| `/api/v2/access_token` | да | JWT по appId, clientSecret, apiKey, срок из exp |
| `/api/1/organizations` | да | проверка организации и области ключа |
| `/api/reporting/v1/olap/columns/get` | да | реальные доступные поля SALES и их возможности |
| `/api/reporting/v1/olap/get` | да | продажи, количество, отдельный отчёт уникальных заказов |
| `/api/employees/v1/employee/list` | да | сотрудники с filters, fields, limit, offset и проверкой принадлежности к организации |
| `/api/employees/v1/attendance/list` | да | явки с organizationId, employeeIds, startAt, endAt, limit, offset |

`POST /api/1/employees/shift/is_open` также есть в спецификации, но возвращает только `isSessionOpened` для сотрудника и терминальной группы, без истории и фактических времени начала/конца. Клиент не опрашивает его массово: переход между опросами не доказывает момент закрытия и не позволяет восстановить пропущенную смену.

У `GetOlapReportRequest` нет поля organizationId. Приложение разрешает отчёты только ключу, у которого `/organizations` вернул ровно указанную организацию. Это предотвращает незаметное смешение нескольких заведений. Для GREEN ROOM используйте отдельный ключ с одной подключённой точкой.

## OLAP

Каждый запрос сначала проверяет metadata. Поля `OpenDate.Typed`, `DishGroup`, `DishName` должны поддерживать grouping; `DishAmountInt`, `DishDiscountSumInt` — aggregation; `OpenDate.Typed` — filtering. Метаданные кэшируются в памяти на час. Отчёты кэшируются на минуту, максимум 16 диапазонов и суммарно 50 000 строк; более крупный отдельный отчёт возвращается полностью, но не кэшируется. Возвращаемые коллекции копируются.

Период — полуинтервал `[from,to)`. Фильтр DateRange содержит `includeLow:true`, `includeHigh:false`. Запрос ограничен 30 днями, чтобы соблюсти документированное ограничение CUSTOM до 31 дня включительно. Большие периоды делятся на непересекающиеся интервалы. Общие чеки запрашиваются отдельным OLAP без товарных группировок, с агрегатом `UniqOrderId`, в том числе при наличии строковых идентификаторов заказа. При наличии обоих источников их результаты должны совпадать; несовпадение возвращается ошибкой. Его значения по непересекающимся `OpenDate.Typed` складываются: заказ относится к одному операционному дню открытия. Количество строк не используется как количество чеков.

Для чеков с десертами нужен именно ID заказа. Статический список таких полей в Cloud OpenAPI отсутствует. Приложение использует поле только если **официальные метаданные текущего сервера** одновременно сообщают `canGroup:true`, `type:ID`, точное смысловое имя `Order ID`, `Unique order ID`, `ID заказа`, `Идентификатор заказа`, `Уникальный идентификатор заказа` или `Уникальный ID заказа`. В запрос передаётся возвращённое `name`, например `UniqOrderId.Id`, если это реально предоставлено сервером. Сам `UniqOrderId` никогда не рассматривается как идентификатор. Если доказанного поля нет, чеки с десертами и доля недоступны. Не используются суммы счётчиков по отдельным позициям. Для продуктовых правил `DishId` также включается только после обнаружения в metadata как группируемого ID/STRING. Неподдерживаемые правила по product ID не заменяют продажи фиктивными значениями.

Знаки сумм и дробного количества сохраняются без float64. `DishDiscountSumInt` — сумма после скидок. Для сверки с финансовым отчётом iikoOffice обязательно проверить на реальных ключах особенности удалённых строк, возвратов и отмен. Клиент не придумывает значения ENUM-фильтров и всегда сообщает об этом ограничении в отчёте.

Официальный Cloud-контракт DateRange задаёт только даты yyyy-MM-dd. Достоверная фильтрация произвольных часов пока не подтверждена. Поэтому запрос продаж за явку/личную смену, сравнение утра и вечера возвращают `ErrUnsupportedInterval`; диапазон не расширяется до целого дня. Поля времени заказов `OpenTime`/`CloseTime` теперь подтверждены для группировки и используются в кассовом OLAP-отчёте. Это не даёт фактических интервалов личных смен. Автоматическая рассылка строит только один завершённый учётный день без сменных уведомлений.

OLAP не имеет пагинации по строкам в проверенной спецификации. Ответ ограничен 32 MiB и 250 000 строк суммарно; при превышении возвращается ошибка с предложением сузить период. Молчаливое усечение запрещено. Методы employees/attendance используют limit/offset, дедуплицируют ID и имеют защитный предел 10 000 записей. totalCount определяет завершение даже если сервер уменьшает размер страницы; пустая или повторяющаяся страница до завершения считается ошибкой. Сотрудники запрашиваются с id/name/mainOrganizationId/organizationIds: локальная проверка включает как основную организацию, так и дополнительное назначение, не исключая бариста с основной организацией в другой точке.

## Явки и PersonalShift

`attendance` относится к табелю; это **не** история PIN-входов и **не** доказательство закрытия личной смены. `startAt`/`endAt` — подтверждённые отметки табеля, `personalStartAt`/`personalEndAt` — зарегистрированные POS-отметки явки. Они показаны раздельно. Timestamp без явного offset отклоняется, чтобы не выдумывать временную зону.

`PersonalShift` в официальной схеме:

```json
[{
  "eventType": "PersonalShift",
  "eventTime": "2026-11-10 15:04:05.123",
  "organizationId": "configured-organization-id",
  "correlationId": "event-correlation-id",
  "eventInfo": {
    "id": "employee-id",
    "roleId": null,
    "opened": false,
    "terminalGroupId": "terminal-group-id"
  }
}]
```

`eventTime` — UTC. `eventInfo.id` — **ID сотрудника**, не ID смены. В событии нет начала, конца и уникального ID смены. Можно наблюдать время ранее полученного события открытия того же сотрудника/терминальной группы, но это не подтверждённая фактическая POS-метка начала. При пропущенном открытии интервал не восстанавливается предположением. [Официальное руководство вебхуков](https://api.iiko.help/docs/guides/webhooks/) предписывает передавать настроенный `authToken` в заголовке `Authorization` буквально, без автоматически добавляемого `Bearer`. Публичная регистрация webhook приложением не выполняется.

Все продакшен-изменения iiko (clockin, clockout, заказы, документы, webhook settings) отсутствуют в клиенте.

## Кассиры и кассовые смены по продажам — проверка 19.11.2026

Снимок OpenAPI обновлён 19.11.2026: версия 3.0.4, 417 путей. Read-only проверка текущего подключения дала HTTP 200 для авторизации и SALES-метаданных (271 поле), HTTP 401 для `employee/list`, `attendance/list`, `employees/couriers` и `employees/info` даже для ID сотрудника из OLAP. Это отказ авторизации конкретного контура, а не доказательство определённой настройки прав. Кадровый справочник и явки не подменяются другим источником и продолжают возвращать исходную ошибку.

Метаданные подтверждают доступные группировки `Cashier.Id` (`ID_STRING`), `Cashier`, `SessionID` («ID кассовой смены»), `SessionNum`, `OpenTime`, `CloseTime` и конкретный ID заказа. Реальный однодневный `Workforce`-отчёт успешно вернул двух кассиров и две кассовые смены. Диагностика выводила только статусы, количество и формат полей: имена, ID чеков и финансовые суммы не сохранялись.

`Workforce` — отдельный отчёт о **кассирах чеков** (`Cashier`) и **кассовых сменах, наблюдаемых по продажам**. Это не полный список работников, не личные смены, не явки и не история PIN-входов. Все суммы ограничены выбранными операционными днями `OpenDate.Typed`; начатая раньше или продолжающаяся позже кассовая смена представлена только продажами внутри выбранного периода.

Один OLAP-запрос на каждые максимум 30 дней одновременно группирует дату, ID/имя кассира, ID/номер кассовой смены, время открытия/закрытия заказа и конкретный ID заказа. Товарных группировок нет. По каждому конкретному заказу проверяется `UniqOrderId == 1`; разные заказы учитываются по реальному ID. Повторная строка того же заказа либо противоречащие назначения кассира/кассовой смены/времени возвращают ошибку целого отчёта. Суммы и дробное количество вычисляются точной арифметикой. Сбой любого следующего диапазона не превращается в частичный отчёт.

`FirstOrderOpened` — минимум времени открытия **заказа**, `LastOrderClosed` — максимум времени закрытия **заказа**. Эти значения не показывают фактические начало и конец работы человека либо кассовой смены и не подтверждают её закрытие. Полученные от OLAP локальные ISO-времена интерпретируются в настроенной временной зоне заведения; явные RFC3339-смещения сохраняются. При отсутствии части отметок соответствующая граница недоступна с предупреждением. Чеки с явно пустым ID кассира не пропадают из сумм: они находятся в строке «Кассир не указан» без фиктивного ID.

Снимки кэшируются только в памяти на минуту: максимум 16 диапазонов и суммарно 10 000 агрегированных строк сотрудников/кассовых смен. Выбор человека и кассовой смены использует тот же снимок, без запросов на каждый элемент.
