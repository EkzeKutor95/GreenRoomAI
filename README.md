# GREEN ROOM AI

Самостоятельное Go-приложение для GREEN ROOM: **iiko Cloud → расчёты Go → Telegram**. Без БД, Docker и вмешательства в iikoFront. Все операции iiko — read-only. Исходники находятся в репозитории; зависимости, кэш и бинарники создаются локально внутри директории проекта.

## Быстрый запуск на macOS / Linux

Требуется Go 1.23 или новее. На этом Mac проверена Go 1.23.4 / macOS arm64.

```sh
cd GreenRoomAI
cp .env.example .env
chmod 600 .env
```

Заполните в `.env` перевыпущенные `IIKO_CLIENT_SECRET`, `IIKO_API_KEY`, токен бота `TELEGRAM_BOT_TOKEN`, свой числовой Telegram ID в `TELEGRAM_ALLOWED_USER_IDS` и `TELEGRAM_REPORT_CHAT_ID`. Также заполните `IIKO_APP_ID` и `IIKO_ORGANIZATION_ID` из своего подключения iiko. Используйте API-ключ, ограниченный **одной организацией GREEN ROOM**: OLAP-контракт не содержит organizationId, и приложение откажется строить отчёт при неоднозначной области ключа.

```sh
make check-config  # Проверка обязательных параметров без сети
make check-api     # Авторизация, организации, поля OLAP и Telegram getMe; без отправки сообщений
make run
```

Откройте личный чат с созданным ботом в Telegram и нажмите `/start`. Не запускайте параллельно другой poller/webhook Telegram с тем же токеном. Сервис повторяет временно неудачные read-only запросы и продолжает работу при потере сети. Остановка — Ctrl+C.

Без ключей можно проверить саму сборку и расчёты:

```sh
make demo          # Только синтетические данные, без HTTP и конфигурации
make check         # fmt, vet, тесты, build
make build         # bin/greenroom-ai
make windows       # bin/greenroom-ai-windows-amd64.exe
```

Проверки и демонстрация не отправляют реальные уведомления. Обычный запуск бота и включение автоотчётов отправляют их в настроенный Telegram-чат.

## Перенос на другой компьютер

Клонируйте репозиторий в выбранную папку:

```sh
git clone https://github.com/EkzeKutor95/GreenRoomAI.git GreenRoomAI
cd GreenRoomAI
```

Установите Git и Go 1.23 или новее. На macOS / Linux дополнительно нужен `make`; затем выполните команды быстрого запуска выше. В репозитории нет `.env`, кэшей, технического состояния и готовых бинарников. Заполните новый `.env` по `.env.example` или перенесите существующий `.env` отдельно защищённым способом.

На Windows без `make` используйте PowerShell из папки проекта:

```powershell
Copy-Item .env.example .env
notepad .env
$env:GOCACHE = "$PWD\.cache\go-build"
$env:GOMODCACHE = "$PWD\.cache\go-mod"
$env:GOPATH = "$PWD\.cache\go"
$env:GOTMPDIR = "$PWD\.cache\tmp"
$env:GOTOOLCHAIN = "local"
New-Item -ItemType Directory -Force $env:GOTMPDIR, bin | Out-Null
go build -trimpath -o .\bin\greenroom-ai.exe ./cmd/greenroom
.\bin\greenroom-ai.exe --check-config
.\bin\greenroom-ai.exe --check
.\bin\greenroom-ai.exe
```

Перед запуском на новом компьютере **остановите старую копию бота**: Telegram допускает только один активный long polling для одного токена. Для сохранения offset и меток уже отправленных отчётов можно отдельно перенести `run/state.json`, пока обе копии остановлены. Файл `.lock` не переносите.

## Возможности

- Русское inline-меню: отчёты, сотрудники, смены, позиции, десерты, сравнение, автоотчёты и диагностика.
- Сегодня/вчера, последние 7/10/30 календарных дней включая сегодня, текущий/предыдущий месяц; произвольные даты через календарь. Сравнения последних 7/30 завершённых дней и предшествующих диапазонов, месяцев и двух выбранных диапазонов.
- Выручка после скидок из `DishDiscountSumInt`, количество из `DishAmountInt`, средний чек, группы, ТОП-10/20 и дневная динамика; подписанные значения возвратов сохраняются. Точная арифметика `math/big.Rat`; округление только при представлении денежных сумм.
- Полный CSV со всеми полученными строками OLAP прямо в Telegram. Строки не обрезаются; слишком большой ответ API завершается явной ошибкой. CSV текстовые ячейки защищены от формул.
- «Сотрудники»: кассиры, зарегистрированные в продажах за выбранный период, с выручкой, количеством чеков, единиц и средним чеком. Кадровый справочник и явки остаются отдельным источником, требующим доступности кадрового API.
- «Смены»: кассовые смены, наблюдаемые по продажам, с выбором периода и показателями. Время первого/последнего заказа показано как отметки заказов; оно не выдаётся за начало/окончание смены человека.
- Автоматически отправляется один отчёт за завершённый учётный день: все проданные позиции и суммы только этой даты.
- JWT с повторным использованием и обновлением по `exp`/401; таймауты, ограничение частоты, ограниченные повторы для 429/5xx и транспортных ошибок, `Retry-After`, TLS verification и запрет редиректов с ключами.
- Кэш в памяти: поля OLAP, область организации и ограниченное число краткоживущих отчётов. На диск продажи, чеки, имена сотрудников и отчёты не записываются.
- Атомарный технический JSON с offset Telegram, настройкой автоотчётов, хэшами/ID отправленных уведомлений и временем их отправки. Отдельный lock защищает локальную установку от двух процессов.
- Graceful shutdown, JSON-логи `slog`, диагностика из меню. Неавторизованные пользователи и групповые интерактивные запросы не получают бизнес-данные. Автоматические отчёты можно явно направить в закрытую группу через конфиг; её состав контролирует владелец.

## Честные границы данных iiko

Официальная спецификация проверена и сохранена в `docs/iiko-openapi.json`; детали, точные методы и схемы — в [docs/API.md](docs/API.md).

**Уникальные чеки и десерты.** `UniqOrderId` является агрегатом количества, а не ID конкретного заказа. Он запрашивается отдельным отчётом без товарной группировки. Суммировать это поле по блюдам нельзя. Если live metadata предоставляет группируемый идентификатор заказа с подтверждённой семантикой, позиции связываются по нему, и чек с несколькими десертами учитывается один раз. Если такого поля нет, число чеков с десертами, без десертов и доля показаны как **недоступные**. Количество и выручка десертов остаются доступны по группам. Категории и product ID задаются в `.env`; конфигурация ID без доступного поля идентификатора товара приводит к явной ошибке, а не заниженному результату.

**Удаления и возвраты.** Приложение сохраняет знак денег и дробного количества. Универсальные непроверенные фильтры отмен не подставляются. Достоверность конкретных правил OLAP и прав ключа необходимо сверить с контрольным отчётом iikoOffice на ваших данных: это указано и в отчётах. Проникновение десертов при доступном ID считается по положительному нетто-количеству десертов в чеке; возврат в отдельном чеке сохраняет собственный ID.

**Личные смены.** `shift/is_open` возвращает текущее состояние и не даёт историю фактических интервалов. `PersonalShift` содержит employee ID, terminalGroupId, opened и время **события**, но не ID смены и не её фактические начало/окончание. Поэтому приложение не обещает восстановить пропущенные фактические закрытия после перезапуска и не выдаёт явку за личную смену.

**Сотрудники и смены по продажам.** Текущее подключение предоставляет OLAP-поля `Cashier.Id`, `Cashier`, `SessionID`, `SessionNum`, `OpenTime` и `CloseTime`. На них работают кассиры и кассовые смены за выбранный период. Полный кадровый справочник и явки проверены отдельно: текущий сервис возвращает `401`, в том числе после обновления токена. Другие источники ими не подменяются. Работники без продаж в выбранном периоде в кассирском отчёте не появятся. Роль — именно кассир чека; выручка бариста за время фактической работы этим не определяется.

**Внутридневные интервалы.** Поля времени заказов доступны. Основной адаптер продаж сейчас строит отчёты по учётным датам `OpenDate.Typed`, а не по произвольным часам. Достоверные интервалы личных смен кадровый API текущему ключу не предоставляет. Выручка за явку и сравнение фактических личных смен не рассчитываются предположением; кассовые показатели доступны отдельно в «Смены».

**Ежедневный отчёт.** Содержит общую выручку, чеки, количество единиц, средний чек, группы и **все позиции** одного учётного дня iiko. Недельные сравнения, другие даты и плановые окна в него не включаются. Учётная дата берётся из `OpenDate.Typed`; её нельзя автоматически считать произвольным интервалом 07:00–01:00.

## Автоотчёты и восстановление

Включите автоотчёт в меню. Состояние переключателя сохраняется в техническом JSON и переживает перезапуск; `.env` задаёт начальное значение только при первом создании состояния.

```env
AUTO_REPORTS_ENABLED=false
DAILY_REPORTS_ENABLED=true
DAILY_REPORT_HOUR=1
OLAP_DELAY=30m
SHIFT_POLL_INTERVAL=5m
```

- Отправляется **один отчёт за последнюю завершённую учётную дату, для которой наступило время отправки**. При указанных настройках отчёт за 18 ноября становится доступен к отправке 19 ноября после 01:30 по `IIKO_TIMEZONE`.
- Каждый отчёт делает один вызов сервиса продаж для ровно одной даты. Все позиции, количества и выручка относятся к этой дате. Большой текст разбивается на подписанные части одного отчёта, без обрезания списка.
- Утренние/вечерние сообщения, сравнения с прошлой неделей и недельная динамика из автоматической рассылки удалены. В интерактивном меню сравнения периодов остаются доступны.
- После запуска проверяется только последняя дата, для которой наступило время отправки. Накопленные старые дни пачкой не отправляются. Устаревшая настройка `REPORT_RECOVERY_DAYS` больше не используется.
- Существующие метки `daily/YYYY-MM-DD` продолжают работать: уже доставленный дневной отчёт повторно не отправляется. Для другого дня воспользуйтесь обычным разделом «Отчёты», не удаляя техническое состояние.
- `DAILY_REPORTS_ENABLED=false` отключает ежедневную отправку конфигурацией; включите `true`, чтобы переключатель меню управлял ею. Час 1–23 и задержка OLAP задаются в `.env`, текущие значения показывает диагностика.
- При неизвестном результате HTTP-отправки или сбое после доставки до записи файла возможен дубликат. Абсолютной exactly-once гарантии нет. Маркеры хранятся до 90 дней; части помечаются версией, чтобы не смешивать данные разных снимков при повторе.
- После аварийного завершения `.lock` может остаться. Удаляйте его только убедившись, что процесс остановлен. Другой активный Telegram poller вызывает диагностику409 и остановку этой копии.

## Подготовленный PersonalShift webhook

По умолчанию HTTP-сервер выключен. Для локального теста можно указать `WEBHOOK_LISTEN=127.0.0.1:8090` и длинный случайный `WEBHOOK_SECRET`. Обработчик: `POST /webhooks/iiko`, тело — массив событий официальной схемы. Заголовок `Authorization` должен **точно** совпасть с секретом (`authToken` iiko); префикс Bearer автоматически не добавляется.

Приложение само не регистрирует webhook и не меняет настройки iiko. Для будущего публичного режима потребуется HTTPS reverse proxy и отдельная настройка iiko. Сейчас сервер выключен.

Обработчик проверяет весь пакет, авторизацию, организацию и форму события. Подтверждённое событие закрытия только будит существующий ежедневный планировщик; несколько событий объединяются в один технический сигнал в памяти. Отдельных сменных сообщений нет, дата и время отправки дневного отчёта по-прежнему проверяются. HTTP200 возвращается без ожидания OLAP или Telegram; неотправленный дневной отчёт планировщик повторно проверит по своему таймеру. События и данные сотрудников не сохраняются. Историю фактических смен из этих сигналов приложение не выдумывает.

## Необязательный ИИ

Укажите `OPENAI_API_KEY` и при необходимости `OPENAI_MODEL` (пример: `gpt-4.1-mini`, требуется доступ вашего API-аккаунта). Модуль использует официальный Responses API с `store:false`, ограниченным количеством функций и проверкой аргументов в Go.

Модель выбирает период и безопасную функцию отчёта/сравнения. Финансовые расчёты и окончательные числовые показатели формирует Go; свободная финансовая генерация не используется. В режиме вопросов о продажах в API уходят вопрос и ограниченные агрегированные отчёты, без токенов, строк чеков и имён сотрудников. Для распознавания фото передаётся само изображение с видимым на нём текстом (см. ниже). Не вводите секреты в текст вопроса. Причины падения продаж без дополнительных данных не считаются доказанными. Без ключа OpenAI все остальные разделы работают.

## Сборки и macOS launchd

`make build` создаёт `bin/greenroom-ai` для текущей ОС. `make windows` создаёт `bin/greenroom-ai-windows-amd64.exe` для Windows amd64. Бинарники не входят в Git-репозиторий. На Windows перенесите exe и заполненный `.env` в отдельную директорию, запустите из неё. Go и Docker на кассе для запуска бинарника не нужны. Эта работа ничего на кассовом оборудовании не устанавливает. Для службы Windows в будущем потребуется служебная обёртка; бизнес-код платформенно независим.

`deploy/ru.greenroom.ai.plist.example` — необязательный пример launchd. Он **не установлен**. Перед самостоятельной установкой остановите ручной запуск, выполните `make build`, создайте `run/`, замените `__PROJECT_DIR__` абсолютным путём проекта и проверьте права `.env`. Автозапуск и установка службы не выполнялись.

## Структура и тесты

- `cmd/greenroom` — конфигурация, DI, сигнал завершения и необязательный HTTP-сервер.
- `internal/iiko`, `internal/telegram` — HTTP-адаптеры, лимиты и ошибки.
- `internal/analytics` — точные числа, интервалы, агрегация, сравнения и CSV.
- `internal/bot` — авторизация, диалоги, календарь и меню.
- `internal/notify`, `internal/state` — расписание, webhook и технические маркеры.
- `internal/assistant` — ограниченные read-only функции для Responses API.

Production-код использует стандартную библиотеку Go. Поведенческие тесты — Ginkgo/Gomega с обязательным bootstrap, чистые функции — таблицы стандартного testing. HTTP-моки не требуют ключей, БД или контейнеров. `make check` действительно запускает go fmt/vet/test/build; Windows проверяется отдельно `make windows`. Подробный результат текущей проверки — [docs/VALIDATION.md](docs/VALIDATION.md).

На текущем подключении проверены read-only запросы продаж, кассиров и кассовых смен. Итоги новых кассирских/кассовых показателей сверены с общим отчётом за тот же день без вывода сумм. Контрольную финансовую сверку с iikoOffice, реальную Telegram-доставку и настройку отдельного кадрового API владелец проверяет отдельно; `employee/list` и `attendance/list` пока возвращают401.

Официальные источники: [iiko API](https://api-ru.iiko.services/api-docs/docs), [отчёты iiko](https://api.iiko.help/docs/en/guides/analytics-and-reports/), [явки и личные смены](https://api.iiko.help/docs/guides/employee-lifecycle/), [webhooks](https://api.iiko.help/docs/guides/webhooks/), [Telegram Bot API](https://core.telegram.org/bots/api), [OpenAI Function Calling](https://developers.openai.com/api/docs/guides/function-calling).

## Диагностика выполнения OLAP

`make check-api` проверяет выдачу токена, организацию, список полей и Telegram getMe. Выполнение отчёта проверяется отдельно:

```sh
make diagnose-iiko                 # вчера, без Telegram long polling и отправки сообщений
make diagnose-iiko DATE=2026-11-12  # конкретный завершённый день
```

Ключи читаются из локального `.env`, но не выводятся. В stdout попадают только стадии, HTTP-коды, количество строк, названия полей, длительности и проверенные UUID correlation ID. Строки отчёта, денежные суммы и персональные данные не сохраняются и не выводятся. До восьми вариантов запроса ограничены одним завершённым днём; при отказе минимального запроса остальные варианты пропускаются. Каждая OLAP-проверка выполняется один раз, кроме одной повторной попытки после обновления токена при401; preflight организации и полей использует стандартную ограниченную retry-политику. Общий таймаут — три минуты.

Проверяются официальный минимальный запрос с группировкой по дате, добавление количества и группировок, ID товаров/заказов при наличии в metadata, отдельный подсчёт чеков и точные варианты основного приложения. Журнал различает `sales_detail` и `receipt_totals`. Диагностика не меняет отчёты на неполные данные и не запускает второй Telegram poller.


## Проверка сотрудников и кассовых смен

```sh
make check-workforce                 # предыдущий учётный день
make check-workforce DATE=2026-11-18
```

Это read-only проверка нового OLAP-источника. Она выводит дату, роль, число кассиров/кассовых смен и источник; имена, ID заказов и суммы не печатаются, Telegram-сообщения не отправляются. Успех этой проверки не означает, что отдельный кадровый API начал принимать ключ.

## Распознавание фото в Telegram

Отправьте боту фотографию чека или рукописной записи в личный чат. Можно нажать **«Распознать фото»** или отправить `/photo` для инструкции. JPEG/PNG также можно прислать как документ, чтобы Telegram не сжимал мелкий текст.

Нужен собственный ключ OpenAI API в `.env`:

```env
OPENAI_API_KEY=ваш_ключ_OpenAI_API
OPENAI_VISION_MODEL=gpt-4.1-mini
```

Если `OPENAI_VISION_MODEL` отсутствует, используется `OPENAI_MODEL`. Ключ нельзя отправлять боту или включать в фото. После изменения `.env` остановите текущего бота Ctrl+C и запустите `make run` заново. `make check-config` показывает, настроено ли распознавание, без вывода ключа. Наличие ключа не проверяет доступность модели или квоту API. Запросы распознавания оплачиваются по вашему аккаунту OpenAI API; подписка ChatGPT сама по себе ключ не задаёт.

Фото передаётся в OpenAI через Responses API для чтения текста. Telegram-ссылка с токеном не передаётся модели: приложение скачивает файл в память и отправляет base64-изображение. Локально фото, текст и имена на нём не сохраняются, в техническое JSON-состояние не попадают. Для Responses задано `store:false`; это не обещание отсутствия хранения на стороне провайдера согласно его политике.

Лимиты приложения: JPEG/PNG, до 10 МиБ и 24 мегапикселей. PDF, HEIC и остальные форматы пока не поддерживаются. Выбирается вариант фото с максимальным разрешением; если он превышает лимит, приложение просит уменьшить файл. Автоматически подменять его менее чёткой версией нельзя. Проверяются metadata и фактический размер потока, MIME определяется по содержимому. Скачивание ограничено 30 секундами, OpenAI — 90 секундами, общий сценарий — двумя минутами.

Результат — **черновик транскрипции** с сохранёнными строками и разделением печатного/рукописного текста. Неуверенные места помечаются `[неразборчиво]`; блики, низкое разрешение и другие ограничения отмечаются отдельно. Имена и суммы нужно сверить с оригиналом. Приложение не суммирует распознанные цифры и не использует их как подтверждённые показатели продаж. Доступ к скачиванию и модели разрешён только allowlisted пользователям в личном чате.

Официальные контракты: [Telegram getFile](https://core.telegram.org/bots/api#getfile), [OpenAI Images and Vision](https://developers.openai.com/api/docs/guides/images-vision?api-mode=responses).
